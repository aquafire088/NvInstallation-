01

Ouvrir la réunion

Les trois premières minutes : se présenter, annoncer l'objet, poser la question. Parler lentement — c'est le moment où l'on est le plus tendu.

À compléter avant la réunion

Les passages surlignés sont à remplacer par vos informations. Les dire une fois à voix haute avant d'entrer dans la salle.

Ce que je dis — se présenter

Bonjour à tous. Merci d'être présents.

Je me présente : je m'appelle votre prénom et nom, je suis votre fonction chez structure.

Je m'occupe de l'installation du serveur du laboratoire.

Ce que je dis — annoncer l'objet et la durée

Nous sommes réunis aujourd'hui pour décider comment nous allons installer ce serveur.

La réunion devrait durer environ trente minutes. Je vous propose de procéder en trois temps : d'abord je présente les deux méthodes possibles, ensuite nous en discutons, et enfin nous décidons ensemble.

N'hésitez pas à m'interrompre si quelque chose n'est pas clair.

Poser la question

Présenter les deux options de façon neutre. Si l'on donne son avis tout de suite, la discussion est fermée avant d'avoir commencé.

Ce que je dis — la question

Nous avons deux méthodes possibles.

La première est l'installation manuelle : on configure chaque étape à la main, depuis l'interface de Windows Server.

La seconde est l'installation automatisée : un script fait tout, et l'on n'intervient pas.

Les deux donnent le même résultat. La différence est le temps, la maîtrise, et ce qui se passe le jour où il faut recommencer.

Alors, quelle méthode préférez-vous pour cette première installation ?

CritèreInstallation manuelleInstallation scriptée
Durée Longue — il faut rester devant Longue aussi, mais sans personne devant
On voit ce qui se passe Oui, écran par écran Seulement dans le journal
Refaire à l'identique Difficile — des écarts à chaque fois Garanti — les mêmes réglages
En cas d'erreur On corrige tout de suite Le script s'arrête et note la raison
Formation de l'équipe On apprend en faisant Il faut lire le script

Proposer de commencer par la méthode manuelle

C'est votre proposition. L'argument le plus solide n'est pas « c'est plus simple » — c'est que la manuelle sert de référence pour valider le script.

Ce que je dis — ma proposition

Si vous me permettez, je vais donner mon avis.

Je propose de commencer par l'installation manuelle, pour cette première fois.

Pour trois raisons.

Premièrement, nous voyons chaque étape. Si quelque chose ne va pas dans ce laboratoire — une carte réseau, un disque, une version de Windows — nous le voyons tout de suite, et pas à la fin.

Deuxièmement, l'installation manuelle nous donne une référence. Nous saurons exactement à quoi doit ressembler un serveur correct. Sans cette référence, on ne peut pas vérifier que le script a bien travaillé.

Troisièmement, cela nous permet de valider le script. Nous le lancerons ensuite sur une machine de test, et nous comparerons les deux résultats.

Donc : la première installation à la main, et les suivantes avec le script. Est-ce que cela vous convient ?

Si on me répond « pourquoi ne pas lancer le script tout de suite ? »

C'est une bonne question. Le script est prêt, et il fonctionne.

Mais il n'a pas encore tourné sur ce matériel. Je préfère que la première installation serve de référence, et que le script soit validé ensuite.

Si nous lançons le script en premier et qu'un problème apparaît, nous ne saurons pas si le problème vient du script ou du serveur.

Si on me répond « la méthode manuelle prend trop de temps »

Vous avez raison, c'est plus long cette fois-ci.

Mais c'est la seule fois. Ensuite le script prend le relais, et nous gagnons du temps à chaque installation suivante.

Je peux aussi faire l'installation manuelle en dehors des heures de service, pour ne gêner personne.

Ce que je dis — conclure la décision

Très bien. Si je résume : nous commençons par une installation manuelle sur le serveur du laboratoire.

Je note tout ce que je fais, étape par étape. Ensuite je lance le script sur une machine de test, et je vous présente la comparaison.

Je vous propose de faire le point la semaine prochaine. Est-ce que tout le monde est d'accord ?

02

Le projet en une phrase

Commencer simple. Une phrase, puis on développe. Ne pas entrer dans la technique tout de suite.

Ce que je dis — ouverture

Bonjour. Je vais vous présenter un projet d'automatisation.

Le but est simple : installer un serveur complet pour un laboratoire d'analyses médicales, sans intervention manuelle.

On lance une seule commande, et le serveur se configure tout seul. Il redémarre quand il faut, et il continue tout seul après chaque redémarrage.

Le serveur remplit quatre rôles : contrôleur de domaine Active Directory, serveur DNS, serveur de fichiers, et serveur de base de données SQL Server.

Ce que je dis — les rôles

Le serveur fait quatre choses. Il gère les comptes utilisateurs avec Active Directory. Il fait la résolution de noms avec le DNS. Il partage des dossiers sur le réseau. Et il héberge les bases de données du laboratoire.

03

Le problème que ça règle

C'est la partie qui justifie tout le reste. Un jury ou un collègue veut savoir pourquoi, pas seulement comment.

Ce que je dis — avant / après

Avant, l'installation se faisait à la main. Il fallait environ une journée de travail, et il fallait rester devant l'écran.

Le technicien cliquait, attendait, redémarrait, puis recommençait à l'étape suivante. À chaque installation, les réglages étaient un peu différents.

Maintenant, tout est écrit dans un seul fichier de configuration. Le résultat est toujours identique. Et le technicien peut partir pendant que ça s'installe.

Si on vous demande un chiffre

Ne pas inventer de mesure. Dire : « Je n'ai pas mesuré précisément, mais le gain principal n'est pas le temps — c'est que le résultat est reproductible. »

04

Comment ça marche

Quatre fichiers à connaître. C'est le cœur de l'exposé.

FichierRôleComment le dire
config.json Toutes les valeurs : adresse IP, nom du domaine, mots de passe « Le fichier de réglages »
Deploy.ps1 Le chef d'orchestre : lit la configuration, lance les étapes dans l'ordre « Le script principal »
state.json La liste des étapes déjà terminées « La mémoire du script »
deploy.log Le journal horodaté de tout ce qui s'est passé « Le journal »
Ce que je dis — les quatre fichiers

Il y a quatre fichiers importants.

config point json contient tous les réglages : l'adresse IP, le nom du domaine, les mots de passe. C'est le seul fichier que l'on modifie.

Deploy point p s un est le script principal. Il lit la configuration et lance les étapes dans l'ordre.

state point json est la mémoire du script. Il retient les étapes déjà terminées.

Et deploy point log est le journal. Il note tout, avec l'heure.

Le point le plus intéressant : survivre au redémarrage

Trois étapes obligent la machine à redémarrer. Un script normal s'arrêterait là. Celui-ci enregistre une tâche planifiée qui s'exécute au démarrage sous le compte SYSTEM, relance Deploy.ps1 -Resume, saute les étapes déjà faites, et se supprime elle-même à la fin.

Ce que je dis — la reprise automatique

Voici la partie la plus intéressante.

Trois étapes obligent le serveur à redémarrer. Normalement, un script s'arrête à ce moment-là, et il faut le relancer à la main.

Ici, le script crée une tâche planifiée qui se déclenche au démarrage de Windows. Elle relance le script, qui consulte sa mémoire, saute les étapes déjà faites, et continue.

La tâche s'exécute sous le compte SYSTEM. C'est important : il n'y a donc aucun mot de passe enregistré sur la machine. Et à la fin, la tâche se supprime toute seule.

05

Les dix étapes

Ne pas lire les dix une par une : c'est long et le public décroche. Annoncer les trois groupes, puis détailler seulement les étapes 7, 8 et 9.

Ce que je dis — annoncer le plan

Il y a dix étapes, que je regroupe en trois parties.

D'abord, la préparation du système : le réseau, les rôles Windows, le domaine.

Ensuite, la configuration du service : le DNS, le DHCP, les utilisateurs.

Enfin, les données : la copie des fichiers, SQL Server, et les bases de données.

Je vais détailler les trois dernières, qui sont les plus intéressantes.

00

Réparation de Windows Update redémarre

DISM /restorehealth, vide le cache, active .NET 3.5. Optionnelle.

01

Réseau et identité redémarre

Adresse IP fixe, renomme la machine et le compte administrateur, active le Bureau à distance.

Ce que je dis

L'ordre est important ici. On configure le réseau d'abord, et on renomme le compte administrateur en dernier. Sinon Windows ne retrouve plus le compte et l'étape échoue.

02

Installation des rôles redémarre

.NET 3.5, Active Directory, DNS, et DHCP si activé dans la configuration.

03

Promotion en contrôleur de domaine redémarre

Crée une nouvelle forêt DOMLABO.LOCAL.

04

Configuration du DNS

Zone directe et zone inverse, redirecteurs vers 8.8.8.8, route par défaut.

05

Configuration du DHCP

Étendue, exclusions, et une stratégie par service. Désactivée dans la configuration actuelle.

Ce que je dis — si on le remarque

Le DHCP est désactivé pour l'instant, parce que les postes ont une adresse fixe. Mais le script est prêt : il suffit de mettre vrai dans le fichier de configuration.

06

Unités d'organisation et utilisateurs

Quatre unités — Accueil, Prélèvement, Technicien, Biologiste — et sept comptes utilisateurs.

Ce que je dis

Le script crée quatre unités d'organisation, une par service du laboratoire : l'accueil, le prélèvement, les techniciens, et les biologistes. Puis il crée les comptes des utilisateurs dans la bonne unité.

07

Copie des données et partages réseau

robocopy depuis la clé USB vers le disque du serveur, puis création des partages SMB.

Ce que je dis

Cette étape copie les données depuis une clé USB vers le disque du serveur, puis elle partage ces dossiers sur le réseau.

J'utilise robocopy et non une simple copie. Pourquoi ? Parce que ce sont plusieurs gigaoctets, et robocopy sait reprendre après une erreur.

Un détail important : robocopy ne renvoie pas zéro quand tout va bien. Il renvoie un quand des fichiers ont été copiés. Tout ce qui est en dessous de huit est un succès. Il faut le savoir, sinon le script croit qu'il a échoué.

08

Installation de SQL Server

Monte l'image ISO copiée à l'étape 7, installation silencieuse, puis SSMS.

Ce que je dis

Le script cherche l'image ISO à trois endroits, dans l'ordre : le nom attendu, puis n'importe quel fichier ISO de plus de trois cents mégaoctets dans le dossier, et enfin le téléchargement.

Le deuxième point est pratique : on peut copier une image depuis une clé USB sans la renommer.

Avant de commencer, le script fait une vérification rapide : il contrôle que le compte administrateur existe bien dans le domaine, et qu'il reste assez de place sur le disque. Sans ça, l'erreur n'apparaîtrait qu'au bout de vingt minutes.

09

Restauration des bases de données

Restaure Prolab.bak et dblog.bak, redémarre SQL, exécute la requête, attribue db_owner.

Ce que je dis

La dernière étape restaure les deux bases du laboratoire : Prolab, la base métier, et dblog, la base de journalisation.

Ensuite le script active le mode d'authentification mixte, puis il redémarre SQL Server — c'est obligatoire pour que le changement soit pris en compte. Et il attend que le service réponde vraiment avant de continuer.

Enfin il crée l'utilisateur Prolab, et il le déclare propriétaire des deux bases.

06

Les postes de travail

Un script séparé, un seul fichier à copier sur chaque poste.

.\Join-Domain.ps1 -Hostname TECH-01 -IPAddress 192.168.1.101
Ce que je dis

Le serveur ne suffit pas : il faut aussi préparer les postes de travail.

Ce deuxième script fait trois choses : il met une adresse IP fixe, il renomme le poste, et il le joint au domaine.

Le renommage et la jonction se font en une seule opération. Si on renommait d'abord, la machine s'enregistrerait dans le domaine sous son ancien nom, et il faudrait deux redémarrages.

Avant de joindre, le script vérifie qu'il trouve le contrôleur de domaine. C'est la panne la plus fréquente : le poste utilise encore un DNS public, donc il ne trouve pas le domaine — et le message d'erreur de Windows ne le dit pas clairement.

ServicePréfixeAdresses
AccueilACC-.50 – .74
PrélèvementPREV-.75 – .99
TechnicienTECH-.100 – .124
BiologisteBIO-.125 – .149
Ce que je dis — la convention de nommage

Les noms des postes suivent le service : ACC pour l'accueil, TECH pour les techniciens, et ainsi de suite.

Ce n'est pas seulement cosmétique. Les stratégies DHCP du serveur reconnaissent ces préfixes pour attribuer la bonne plage d'adresses. Aujourd'hui le DHCP est désactivé, mais si on l'active plus tard, rien n'est à renommer.

07

La démonstration

Ne pas lancer une installation complète devant un public : c'est trop long. Montrer plutôt la configuration, le journal, et le résultat.

# 1 — montrer les réglages
notepad .\config.json

# 2 — montrer la mémoire du script
Get-Content .\state.json

# 3 — montrer le journal en direct
Get-Content .\deploy.log -Wait

# 4 — montrer le résultat
Get-ADUser -Filter * | Select-Object Name, Department
Get-SmbShare
sqlcmd -S ".\SQLEXPRESS" -E -Q "SELECT name FROM sys.databases"
Ce que je dis — pendant la démonstration

Je ne vais pas lancer l'installation complète, parce qu'elle dure environ une heure. Je vais plutôt vous montrer le résultat.

Voici le fichier de configuration. Vous voyez : tout est ici, l'adresse, le domaine, les bases de données.

Voici le journal. Chaque ligne est horodatée, et chaque étape indique si elle a réussi ou échoué.

Et voici le résultat : les utilisateurs dans l'annuaire, les dossiers partagés, et les bases de données restaurées.

Si la démonstration échoue en direct

Rester calme et utiliser le journal : « Justement, c'est pour ça que le script écrit un journal. Regardons la dernière ligne. » Une panne expliquée est plus convaincante qu'une démonstration parfaite.

08

Les questions probables

Les réponses sont courtes volontairement. Une question mérite trois phrases, pas un paragraphe.

Pourquoi PowerShell et pas un autre outil ?
Ma réponse

Parce que PowerShell est déjà installé sur Windows Server. Il n'y a rien à ajouter, aucune dépendance. Et il donne un accès direct à Active Directory, au DNS et au DHCP.

Que se passe-t-il si une étape échoue ?
Ma réponse

Le script s'arrête et écrit la raison dans le journal. Il ne continue pas, parce que les étapes dépendent les unes des autres.

On corrige le problème, puis on relance la même commande. Le script saute les étapes déjà terminées et reprend à celle qui a échoué.

Peut-on relancer le script deux fois sans casser le serveur ?
Ma réponse

Oui. Chaque étape vérifie d'abord si le travail est déjà fait. Si l'utilisateur existe, elle ne le recrée pas. Si le partage existe, elle le laisse en place.

Une seule exception : la requête SQL personnalisée. Elle crée un utilisateur sans vérifier, donc elle échoue si on la relance. C'est un point que je connais.

Et les mots de passe dans le fichier de configuration ?
Ma réponse

C'est la principale limite du projet. Les mots de passe sont en clair dans config point json.

Le fichier est exclu du dépôt Git, donc il n'est jamais publié. Mais pour un usage en production, il faudrait les chiffrer.

Les utilisateurs n'ont pas de mot de passe ?
Ma réponse

Non, c'est volontaire pour le laboratoire, qui est un réseau isolé.

Sur un réseau ouvert, ce serait inacceptable. Il faudrait un mot de passe initial et le changement obligatoire à la première connexion.

Combien de temps prend l'installation complète ?
Ma réponse

Environ une heure, dont la plus grande partie est l'installation de SQL Server et la copie des données.

Mais le point important n'est pas la durée : c'est que personne n'a besoin de rester devant.

Est-ce que ça marche sur une autre version de Windows Server ?
Ma réponse

Je l'ai testé sur une machine virtuelle. Les commandes utilisées existent depuis Windows Server 2012, donc en principe oui — mais je ne peux pas l'affirmer sans l'avoir testé.
